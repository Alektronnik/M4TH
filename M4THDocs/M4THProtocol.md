# M4TH Protocol

**Monorepo formal-package standard for M4TH — Alektronnik mathematics.**

This document defines the complete protocol for packages under the `M4TH/`
monorepo.  It fuses the T-ORIK4 package standard (`T-ORIK4/README.md`) and the
live-layer standard (`T-ORIK4/README.live.md`) into a single protocol specific
to M4TH.

The M4TH monorepo has two extra requirements not present in T-ORIK4:

- **`.web.lean` files** for Lean v4.33.0-rc1 compatibility (single-file,
  monolithic, for the web environment).
- **`M4TH.sh`** as the unified validation script for build, live, and web
  compilation.

The governing principle is the same:

> A reader must be able to take one package directory under `M4TH/`, inspect it,
> build it against Mathlib, regenerate its native figure, compile its live and
> web variants, and understand its public mathematical content without access to
> any hidden formalization.

---

## I. Directory Layout

Every formal package must live under:

```text
M4TH/<PackageName>/
```

The required structure is:

```text
<PackageName>/
  README.md
  lakefile.toml
  <PackageName>.lean
  <PackageName>.svg
  <PackageName>/
    Basic.lean
    ...
  <PackageName>Live/
    <PackageName>.live.lean
    <PackageName>.live.MANUAL.md
    <PackageName>.web.lean            (optional: only if v4.33.0-rc1 needs fixes)
    <PackageName>.web.README.md       (alongside .web.lean, if present)
```

The `Live` directory is mandatory before a package is considered complete.

The `.web.lean` file is only required when the package uses API names that
differ between Lean v4.31.0 and v4.33.0-rc1.  Packages that compile without
errors on both versions do not need a `.web.lean`.

## II. Package Root

The root file

```text
<PackageName>/<PackageName>.lean
```

has two roles:

1. It is the public root module of the package.
2. It contains the native Lean SVG generator for `<PackageName>.svg`.

The root module must:

- begin with the standard copyright/license header;
- use `module`;
- import `Lean` if it contains the SVG generator;
- publicly import all package modules using namespaced imports;
- contain no private or unpublished imports;
- generate `<PackageName>.svg` through a Lean `#eval`;
- keep graph-generation code auxiliary and isolated in a namespace such as
  `<PackageName>Graph`.

Example:

```lean
module

import Lean

public import PackageName.Basic
public import PackageName.MainTheorem

namespace PackageNameGraph

def defaultOutputPath : System.FilePath :=
  "PackageName.svg"

def writeDefault : IO Unit :=
  IO.FS.writeFile defaultOutputPath svg

end PackageNameGraph

#eval PackageNameGraph.writeDefault
```

The SVG file generated by this command must be kept in the package root:

```text
M4TH/<PackageName>/<PackageName>.svg
```

Forbidden inside a package directory:

```text
<PackageName>/.lake
<PackageName>/lake-manifest.json
<PackageName>/lean-toolchain
```

Use the monorepo root Lake workspace for routine validation:

```text
lake build PackageName
lake env lean PackageName/PackageNameLive/PackageName.live.lean
```

## III. Source Modules

All library source files must live inside the homonymous subdirectory:

```text
<PackageName>/<PackageName>/*.lean
```

Flat source files in the package root are not allowed, except for the root
aggregator `<PackageName>.lean`.

Each source file must:

- begin with the standard header;
- use `module`;
- use namespaced imports;
- prefer `public import` when definitions are part of the package API;
- avoid imports such as `import Basic`, `import Main`, or other local names
  without the package namespace;
- avoid references to unpublished formalizations;
- avoid `sorry`, `admit`, package-local `axiom`, and accidental trusted
  computation such as `native_decide` when a kernel proof with `decide`,
  `norm_num`, `simp`, `omega`, or explicit finite certificates is available.

Accepted import shape:

```lean
public import Mathlib.Tactic
public import PackageName.Basic
```

Rejected import shape:

```lean
import Basic
import RiemannSynthesis
import NavierStokesWeb
import ErdosWeb
```

## IV. Lake Configuration

Every package must contain its own `lakefile.toml`:

```toml
name = "PackageName"
defaultTargets = ["PackageName"]

# PIN OBLIGATORIO: fijar exactamente la revision de Mathlib usada para validar
# este paquete antes del primer `lake build`.
[[require]]
name = "mathlib"
scope = "leanprover-community"
rev = "fabf563a7c95a166b8d7b6efca11c8b4dc9d911f"

[[lean_lib]]
name = "PackageName"
```

The package must also be registered in the monorepo root `lakefile.toml`:

```toml
[[lean_lib]]
name = "PackageName"
srcDir = "PackageName"
```

This gives two valid modes:

```text
# from the M4TH monorepo root
lake build PackageName

# from M4TH/PackageName after pinning Mathlib
lake build PackageName
```

## V. README Standard

Every package README must be public, self-contained, and publication-safe.

It must include:

- package title;
- author;
- license;
- main statement;
- principal Lean definitions and theorems;
- package structure;
- build command;
- axiom-certificate command;
- verification status;
- review items;
- naming notes when useful.

It must not mention:

- unpublished mother formalizations;
- private source files;
- hidden roadmaps;
- "source corpus";
- `RiemannSynthesis.lean`;
- `NavierStokesWeb.lean`;
- `BirchSwinnertonDyerWeb.lean`;
- `ErdosWeb.lean`;
- any other unpublished formalization.

---

## VI. Native SVG Figure

Every complete package must include a native SVG generated from Lean.

The figure must:

- be generated by code inside `<PackageName>.lean`;
- use no Python, Gnuplot, JavaScript, external plotting library, or image asset;
- be mathematically faithful to the formal content;
- include `by Alektronnik`;
- avoid legends or text overlapping mathematical lines;
- avoid misleading visual interpolation;
- distinguish discrete objects from continuous objects;
- use a restrained publication-style palette;
- render cleanly as a standalone SVG.

## VII. Live Layer (.live.lean)

The live layer is for web certification, teaching, and human inspection.

It lives in:

```text
<PackageName>/<PackageName>Live/
```

and contains:

```text
<PackageName>.live.lean
<PackageName>.live.MANUAL.md
```

---

### VII.A. Non-Interference Rule

Creating or updating a live layer must not modify the source package library.

Do not edit:

```text
<PackageName>.lean
<PackageName>/*.lean
README.md
lakefile.toml
<PackageName>.svg
```

unless explicitly correcting the library.

The live workflow is allowed to create or replace only:

```text
<PackageName>Live/<PackageName>.live.lean
<PackageName>Live/<PackageName>.live.MANUAL.md
```

---

### VII.B. Bit-Exactness Standard

The `.live.lean` file must preserve the public source content with maximum
fidelity.

Bit-exactness means:

- definitions, theorem statements, proofs, namespaces, notation, and comments
  from the source modules are preserved;
- mathematical order follows the package dependency order;
- source code is not rewritten for style;
- theorem names are not renamed;
- proofs are not shortened, expanded, or replaced;
- no extra theorem, definition, axiom, example, or graph generator is inserted;
- no unpublished dependency is introduced;
- no local package import remains inside the live file.

The only accepted transformations are structural:

- keep one standard live header;
- keep one `module` command at the top;
- replace package imports with the required public Mathlib imports;
- remove repeated file headers from fused modules;
- insert source-file separators as Markdown-style Lean comments;
- preserve each module body after its imports.

Accepted separator:

```lean
/-!
## Source file: `PackageName/File.lean`
-/
```

---

### VII.C. Live File Header

Every `.live.lean` file must start with the standard public header:

```lean
/-
Copyright (c) 2026 Bezalel Izquierdo Perez. All rights reserved.
Released under Apache 2.0 license as described in the file LICENSE.
Authors: Bezalel Izquierdo Perez
-/
module
```

After `module`, import only public Mathlib dependencies required by the fused
source.

Accepted:

```lean
public import Mathlib.Tactic
public import Mathlib.Analysis.SpecialFunctions.Log.Basic
```

Rejected:

```lean
import PackageName.Basic
public import PackageName.Main
import RiemannSynthesis
import NavierStokesWeb
```

The live file must be self-contained with respect to the package source.

---

### VII.D. Fusion Order

The source files must be fused in dependency order, not alphabetical order.

Use the package imports to determine the order:

```text
Basic
Foundational definitions
Intermediate lemmas
Main structures
Main theorems
Certified examples
Conditional frontier
```

Examples from the current standard:

```text
SU3Concrete:
  GellMann -> LieAlgebra -> StructureConstants -> Commutator -> Representation

MertensPNT:
  Basic -> MertensConstant -> ErdosBlocks -> MertensBridge
  -> TTAOData -> Connections -> PNTFrontier

ZetaZeroCounting:
  Xi -> ZeroCounting -> SafeHeights -> MainTerm
```

The manual must follow the same order.

---

### VII.E. Forbidden Content

The live layer must not contain references to unpublished mother
formalizations, private roadmaps, or hidden source files.

Forbidden imports and references:

```text
RiemannSynthesis
NavierStokesWeb
BirchSwinnertonDyerWeb
ErdosWeb
source corpus
mother formalization
unpublished formalization
formalizacion madre
```

Forbidden Lean constructs in completed live files:

```text
sorry
admit
axiom
native_decide
```

`native_decide` is forbidden in this publication standard because it can add
trusted compiled evaluation to the axiom certificate.  Use kernel-visible
proofs, `decide`, explicit finite certificates, or ordinary Mathlib tactics
instead.

---

### VII.F. Live Manual (.live.MANUAL.md)

The `.live.MANUAL.md` file is a study manual for the `.live.lean` file.

It must:

- be written in English;
- be public and self-contained;
- use a classical technical Markdown style;
- avoid emojis and decorative noise;
- include authorship and license;
- follow the theorem and definition order of the live file;
- explain what is formalized, what is conditional, and what is not claimed;
- include a terminal-style axiom certificate;
- include verification commands;
- avoid marketing language;
- avoid hidden provenance.

#### Manual Header

Every live manual must begin with:

```markdown
# PackageName.live

**Author:** Bezalel Izquierdo Perez
**License:** Apache 2.0
**Live file:** `PackageName.live.lean`
```

#### Manual Structure

Use numbered sections with a sober academic style:

```text
I. Mathematical Aim
II. Source Architecture
III. Foundational Definitions
IV. Main Lemmas
V. Main Theorems
VI. Certified Examples or Data
VII. Conditional Frontiers
VIII. Axiom Certificate
IX. Reading Guide
X. Verification
```

Adapt the sections to the package.  Do not compress a substantial package into
a superficial summary.

#### Axiom Certificate Section

Every live manual must include a terminal-style certificate section:

```text
printf 'import PackageName
#print axioms Namespace.main_theorem_1
#print axioms Namespace.main_theorem_2
#print axioms Namespace.main_theorem_3
' | lake env lean --stdin
```

Expected output:

```text
'Namespace.main_theorem_1' depends on axioms: [propext, Classical.choice, Quot.sound]
```

Any extra axiom must be treated as a defect.

## VIII. Web Layer (.web.lean)

The web layer is a variant of the live layer adapted for Lean v4.33.0-rc1
compatibility on the web environment (live.lean-lang.org).

### VIII.A. When a .web.lean is needed

A `.web.lean` file is required when the package source uses API names that
differ between Lean v4.31.0 and v4.33.0-rc1.  The known name changes are:

| v4.31.0 (.live) | v4.33.0-rc1 (.web) |
|-----------------|---------------------|
| `Set.mem_setOf_eq` | `Set.mem_ofPred_eq` |
| `Nat.infinite_setOf_prime` | `Nat.infinite_setOfPred_prime` |
| `ENat.map_coe` | `ENat.map_natCast` |
| `Nat.cast_zero` (ENat context) | `ENat.natCast_zero` |

Packages that compile without errors on v4.33.0-rc1 using their `.live.lean`
names do not need a `.web.lean`.

### VIII.B. Web File Location

The `.web.lean` file lives alongside the `.live.lean`:

```text
<PackageName>Live/<PackageName>.web.lean
<PackageName>Live/<PackageName>.web.README.md
```

### VIII.C. Web File Rules

- The `.web.lean` is a **copy** of the `.live.lean` with only the API names
  changed to the v4.33.0-rc1 variants.
- It uses the same single-file monolithic structure.
- Mathematical content (definitions, theorems, proofs) is identical to the
  `.live.lean`.
- Only API renaming is allowed.  No new theorems, no proof changes, no
  restructuring.
- If a proof tactic such as `dsimp` or `rfl` behaves differently in
  v4.33.0-rc1, minimal tactic adjustments are permitted.

### VIII.D. Web README (.web.README.md)

Every `.web.lean` must be accompanied by a `.web.README.md` in the same
directory, named `PackageName.web.README.md`.

It must document:

- The exact API changes applied.
- Any tactic adjustments made.
- Verification commands.

Example:

```markdown
# MertensPNT.web.lean — Compatibilidad Lean v4.33.0-rc1

## Cambios respecto a MertensPNT.live.lean

| API v4.31.0 (.live) | API v4.33.0-rc1 (.web) |
|---------------------|-------------------------|
| `Nat.infinite_setOf_prime` | `Nat.infinite_setOfPred_prime` |

## Fixes adicionales

- `summable_mertensCorrectionIndexed`: `dsimp` replaced by explicit `rfl`.

## Verificacion

grep -c 'Nat.infinite_setOfPred_prime' MertensPNT.web.lean   # debe dar 7
grep -c 'Nat.infinite_setOf_prime[^P]' MertensPNT.web.lean   # debe dar 0
```

## IX. Axiom Certificate

Each package README must provide an axiom-certificate command.

The expected output for representative package theorems is:

```text
[propext, Classical.choice, Quot.sound]
```

Any additional axiom must be treated as a defect unless deliberately justified.

Recommended command shape:

```text
echo 'import PackageName
#print axioms Namespace.main_theorem_1
#print axioms Namespace.main_theorem_2
#print axioms Namespace.main_theorem_3' \
  | lake env lean --stdin
```

## X. M4TH.sh Validation Script

The `M4TH.sh` script in the monorepo root provides unified validation for all
packages.

### Usage

```text
./M4TH.sh all                Build all + compile all .live.lean + .web.lean
./M4TH.sh build              Build all packages via lake build
./M4TH.sh build <Pkg>        Build a single package
./M4TH.sh live               Compile all .live.lean files (bit-exact check)
./M4TH.sh live <Pkg>         Compile .live.lean for a single package
./M4TH.sh web                Compile all .web.lean files (v4.33.0-rc1 check)
./M4TH.sh web <Pkg>          Compile .web.lean for a single package
./M4TH.sh clean              Remove M4TH.log
```

### Log

Each run overwrites `M4TH.log` in the monorepo root.  No `logs/` directory is
created.

### Package List

The script maintains the authoritative list of M4TH packages.  Adding a new
package requires updating the `ALL_PKGS` array in `M4TH.sh`.

## XI. Completion Checklist

Before a package is considered standardized under M4TH:

- [ ] package directory exists under `M4TH/<PackageName>`;
- [ ] source files live under `<PackageName>/<PackageName>/`;
- [ ] root file `<PackageName>.lean` exists;
- [ ] local `lakefile.toml` exists with pinned Mathlib;
- [ ] package is registered in monorepo root `lakefile.toml`;
- [ ] imports are namespaced;
- [ ] no unpublished formalization is imported or cited;
- [ ] README is public and self-contained;
- [ ] SVG generator exists in the root file;
- [ ] `<PackageName>.svg` exists in the package root;
- [ ] `lake build <PackageName>` succeeds;
- [ ] `<PackageName>.live.lean` exists and compiles;
- [ ] `<PackageName>.live.MANUAL.md` exists;
- [ ] `.live.lean` is bit-exact with source modules;
- [ ] axiom certificate is clean (`propext, Classical.choice, Quot.sound`);
- [ ] no `.DS_Store`, `.lake`, `lake-manifest.json`, `lean-toolchain` inside
  the package;
- [ ] forbidden-reference audit clean;
- [ ] `./M4TH.sh live <PackageName>` succeeds;
- [ ] `.web.lean` exists if v4.33.0-rc1 compatibility requires it;
- [ ] `.web.README.md` exists alongside `.web.lean`;
- [ ] `./M4TH.sh web <PackageName>` succeeds (if .web.lean present);
- [ ] no v4.31.0 API names remain in `.web.lean`;
- [ ] no v4.33.0-rc1 API names leak into `.live.lean`.

## XII. Verification Commands

### Structure check

```text
find <PackageName>/<PackageName>Live -maxdepth 1 -type f | sort
```

Expected result (without .web):

```text
<PackageName>/<PackageName>Live/<PackageName>.live.lean
<PackageName>/<PackageName>Live/<PackageName>.live.MANUAL.md
```

With .web variants:

```text
<PackageName>/<PackageName>Live/<PackageName>.live.lean
<PackageName>/<PackageName>Live/<PackageName>.live.MANUAL.md
<PackageName>/<PackageName>Live/<PackageName>.web.lean
<PackageName>/<PackageName>Live/<PackageName>.web.README.md
```

### Bit-exact check

```text
lake env lean PackageName/PackageNameLive/PackageName.live.lean
```

### Web compatibility check

```text
# v4.31.0 names must be zero in .web.lean
grep -c 'Set\.mem_setOf_eq\|Nat\.infinite_setOf_prime\b\|ENat\.map_coe\|Nat\.cast_zero' \
  PackageName/PackageNameLive/PackageName.web.lean

# v4.33.0-rc1 names must be zero in .live.lean
grep -c 'Set\.mem_ofPred_eq\|Nat\.infinite_setOfPred_prime\|ENat\.map_natCast\|ENat\.natCast_zero' \
  PackageName/PackageNameLive/PackageName.live.lean
```

### Forbidden-reference audit

```text
rg -n "RiemannSynthesis|NavierStokesWeb|BirchSwinnertonDyerWeb|ErdosWeb|source corpus|mother formalization|unpublished formalization|formalizacion madre|\\bsorry\\b|\\baxiom\\b|admit|native_decide|^import PackageName|^public import PackageName" \
  <PackageName>/<PackageName>Live
```

## XIV. Current Standard

The standard in this protocol is defined by the current M4TH monorepo state:

- self-contained package directories under `M4TH/`;
- no hidden mother-formalization references;
- per-package `lakefile.toml` + monorepo root `lakefile.toml`;
- root aggregator with native Lean SVG;
- homonymous source directory;
- live layer with bit-exact `.live.lean` and `.live.MANUAL.md`;
- web layer with `.web.lean` and `.web.README.md` for v4.33.0-rc1;
- `M4TH.sh` as unified validation script;
- clean axiom certificate;
- Mathlib-oriented import and module discipline;
- publication-quality mathematical diagrams;
- explicit distinction between proved results, certified data, and conditional
  frontiers.

This is the Alektronnik formal package protocol for `M4TH`.
